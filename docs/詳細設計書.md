## 1. 全体構成

### 1.1 ハードウェア

| 部品 | 型番など | つなぎ方 |
|---|---|---|
| 本体 | Arduino UNO Q（Qualcomm QRB2210 の Linux 側 ＋ STM32U585 のマイコン側） | — |
| 深度カメラ | Orbbec Gemini 335（カラー・深度・IMU） | USB ハブ経由で Linux 側 |
| スピーカーフォン | Anker PowerConf | USB ハブ経由で Linux 側 |
| モニター | 縦置き | USB-C ハブの DisplayPort |
| モータードライバー | L298N ×2（①左・②右、A 側が前輪） | マイコン側の GPIO |
| モーター | Yahboom 520（12V・1:40・ホール式エンコーダー）×4 | L298N、エンコーダーはマイコン側 |
| 電源 | LiPo 12〜13V（モーター用）、UNO Q は USB-C | GND は共通 |

配線表は README の「7. 台車」を参照。

### 1.2 ソフトウェア

| 置き場所 | 実行単位 | 中身 |
|---|---|---|
| UNO Q ホスト | Chromium kiosk | 画面の律（`renderer/index.html?kiosk=1&lite=1`） |
| UNO Q ホスト | arduino-router（システムサービス） | Linux 側とマイコン側の Bridge（MessagePack-RPC） |
| Docker `ritsu-renderer` | nginx :8080 | 画面のファイルを配る・サーバーと rosbridge への中継 |
| Docker `ritsu-rosbridge` | rosbridge_websocket :9090 | WebSocket ⇔ ROS 2 トピック |
| Docker `ritsu-camera` | `ros/ritsu_perception.py` | 顔・人・障害物・傾き・フォローの人の追跡 |
| Docker `ritsu-memory` | `ros/ritsu_memory.py` | 記憶・反応の記録・ニュース |
| Docker `ritsu-base` | `ros/ritsu_base.py` | 台車の制御 |
| マイコン | `arduino/ritsu-base/sketch/sketch.ino`（App Lab アプリ） | 4輪の速さ制御 |
| サーバー | LiteLLM → Ollama、ritsu-stt（faster-whisper :8100）、ritsu-tts（VOICEVOX :50021） | 考える・聞き取り・読み上げ |

- ROS 2 は Jazzy。ROS 2 のコンテナは `network_mode: host` と `ipc: host`（DDS の共有メモリを使うため。無いと別のコンテナからトピックが見えない）。
- ROS 2 のノードはすべて `ritsu-ros` イメージ（`ros/Dockerfile`: rosbridge、Orbbec SDK、OpenCV、YuNet、SFace）から作る。
- `restart: unless-stopped` で、落ちたら Docker が起動し直す。

### 1.3 処理の流れ（概略）

```
スピーカーフォン ⇄ 画面の律(brain.js) ─HTTP→ nginx ─┬→ /llm/ → LiteLLM → Ollama
                                                    ├→ /stt/ → Whisper
                                                    ├→ /tts/ → VOICEVOX
                                                    └→ /rosbridge → rosbridge ⇄ ROS 2 トピック
深度カメラ → ritsu_perception ─(person・obstacle・follow_target)→ ritsu_base ─Bridge→ STM32 → L298N → モーター
                     ↑──────────(/odom・/ritsu/follow)─────────┘
```

| メソッド | 引数 | 内容 |
|---|---|---|
| `base_set` | 4輪の目標の速さ | 速さの PI 制御の目標を変える。返り値でエンコーダーの値・状態を返す |

### 3.2 言葉の見分け（brain.js）

話しかけられた言葉は、上から順に見て最初に当てはまったものを使う。

| 順 | 判定 | 方法 | 結果 |
|---|---|---|---|
| 1 | 止まって | 正規表現 | 台車を止め、順番待ちを飛ばす |
| 2 | 静かに / 話していいよ | 正規表現 | 5分黙る / 取り消す |
| 3 | 決まった動く頼み（`MOVE_COMMANDS`） | 正規表現（follow_off → follow → walk_off → walk → move の順） | 台車へ指示し、用意したセリフで返事 |
| 4 | 動く頼みっぽい | `MOVE_HINT_RE` と頼む言い方 かつ 30文字以内 かつ 質問・体の動きでない | ★ LLM に7択（JSON の enum で縛る）。2.5秒で打ち切り |
| 5 | 訂正 | 「AじゃなくてB」などは正規表現、ほかは LLM | 記憶を直す |
| 6 | それ以外 | — | LLM が返事を作る |

- おさんぽの言葉は、呼びかけ＋「おさんぽ」の一言、「〇〇モード」も受ける。
- 返事・独り言・反応の LLM は LiteLLM の `chat`（gemma3:4b）。`config.js` の `llmModel` か `?model=` で `chat-large` に切り替えられる。

### 3.3 LLM の返答の扱い

- 返答に `[emotion:x][motion:y]` のタグを付けさせ、表情・モーションに使う。
- 知らない表情・モーション名、崩れたタグ、記号、絵文字、名前の前置きを取り除く。長すぎる返答は文の区切りで切る。日本語でない返答は使わない。
- 返事は全部受け取ってから使う（ストリーミングはしない）。読み上げは文ごとに分け、最初の文の声ができたら話し始めて、話している間に次の文を作る。

### 3.4 動いている間と言葉を守る間

| 状態 | 決め方 | 効果 |
|---|---|---|
| `moving` | `/ritsu/base_event` の walk/follow の start で 70秒 / 310秒、stop で今から5秒。頼んだ時点でも5秒入れる | 独り言・しばらく居る人への声かけを止める |
| `protecting` | `_protect(text)` で 今 ＋ (1.2 ＋ 文字数 × 0.17)秒 | 聞かない（`canListen` が false）、独り言・反応を止める |

### 3.5 声（voice.js）

- 音量で声の区間を切り出し、`/stt/` に送って文字にする。律が話している間は声とみなす大きさを上げる（自分の声で割り込まないため）。
- はっきりした声が約0.26秒続くと律の声を止める（`voice.bargeIn`）。
- 読み上げは `/tts/`（VOICEVOX WhiteCUL ノーマル）。読みを直す表（`READ_FIX`）: ℃→度、%→パーセント など。
- マイクの様子を `/ritsu/voice_status` で1秒ごとに送る。

## 4. ROS 2 ノード

### 4.1 ritsu_perception（コンテナ ritsu-camera）

**処理の流れ（1フレームごと）**

1. カラー・深度・IMU を受け取る（`PERCEPTION_FPS` 既定 8 を上限。UNO Q では実際は約1〜4回/秒）。
2. 床を見つける（`Floor`、2秒ごと）: 深度画像の下半分の点に RANSAC で平面を当て、法線が鉛直から45度以内・点の3割以上が乗っていれば、カメラの高さと下向きの角度を求めて平滑化する。急に 0.08m・4度より大きく違う値は、5回続けて出るまで使わない（人の足を床と見ないため）。見つからないうちは `CAMERA_HEIGHT` / `CAMERA_PITCH_DEG`。
3. 深度を床の高さで補正した点（x・前・高さ）にする。
4. 障害物（`detect_obstacles`）: 床から0.06mより高く、0.15m〜3.0m の点を、正面（台車の幅 `ROBOT_HALF_WIDTH` の通り道）・左・右に分け、点が12個以上ある方向だけ一番近い距離を出す。フォロー中はついていく人のまわり0.4mを除く。
5. フォローの開始・終了の頼みを、このカメラの処理の中で反映する（別のスレッドから途中で情報を消さないため）。
6. フォローの人の追跡（`FollowTracker`、4.1.1）。
7. 顔の検出（YuNet、画像を半分に縮めて実行）→ 顔の3次元位置・こちらを見ているか（鼻のずれ / 両目の間隔が `LOOK_YAW` 以内）。
8. マスターの顔の見分け（SFace、1秒に1回。フォロー中は休む）。
9. 画面のすぐ前の手（`TOUCH_DIST` 0.45m より近い物が画像の3%以上）。
10. IMU から傾き。

**見張り**

- カメラから10秒映像が来なければ開き直す。エラーのときもカメラを閉じてから開き直す。
- 見張りのスレッドが、処理が30秒まったく進まなければ（SDK の中で固まった）プロセスを終了する。Docker が起動し直す。

#### 4.1.1 FollowTracker（フォローの人の追跡）

| 段階 | 処理 |
|---|---|
| 地図 | 床から0.2mより高い点を、上から見た5cmマスの地図（左右 ±2m・前 4.5m まで）にする |
| かたまり | つながったマスをまとめる（`connectedComponentsWithStats`）。幅0.15〜0.9m・奥行0.9m以内・床から0.9m（画角の上に出るならその手前）まで届くものを「人くらい」とする |
| 始める | 顔が見えていればその真下のまわり、見えなければ正面30度・3.5m以内でいちばん近い人くらいのかたまり |
| 追う | 前の位置を `/odom` で台車の動きの分だけ補正し、そのまわり（0.45m、見失ってからの時間 × 1.0m/s だけ広げ、上限1.2m）で一番近いかたまり。人が家具とつながっているときは、半径0.22mの窓を寄せていく方法（点が15個以上あれば人がいるとみなす） |
| 確かめる | 顔か人の形で最後に確かめてから8秒たったら見失ったとみなす（家具を追い続けない） |
| 出力 | `/ritsu/follow_target` `{"lost","face","obstacle","x","d"}`（障害物はその人を除いたもの） |

**主なパラメータ**

| 名前 | 既定 | 意味 |
|---|---|---|
| `PERCEPTION_FPS` | 8 | 1秒あたりの処理回数の上限 |
| `CAMERA_ROTATE` | 0 | カメラを縦置きしたときの回転 |
| `FLOOR_AUTO` | 1 | 床を自動で見つける |
| `CAMERA_HEIGHT` / `CAMERA_PITCH_DEG` | 1.0 / 0 | 床が見つからないときのカメラの高さ [m]・下向きの角度 |
| `ROBOT_HALF_WIDTH` | 0.2 | 台車の幅の半分＋余裕 [m] |
| `OBSTACLE_MIN` | 0.15 | 映り込む台車自身を除く距離 [m] |
| `LOOK_YAW` | 0.2 | こちらを見ているとみなす顔の向き |
| `TOUCH_DIST` | 0.45 | 手を合わせる距離 [m] |
| `MASTER_MATCH` | 0.40 | マスターとみなす類似度 |
| `IMU_ROLL_SIGN` | -1 | 傾きの向き |
| `DEBUG_SNAPSHOT` | 0 | 1 で確認用画像を出す |

### 4.2 ritsu_memory（コンテナ ritsu-memory）

- `/ritsu/memory_put` を受けて `data/memory.json` に保存し、`/ritsu/memory` で5秒ごとに送る。
- 保存のたびに `data/backup/memory-日付.json` に控え（14日分）。壊れていたら起動時に一番新しい控えから戻す。
- `/ritsu/log` を `data/log/日付.jsonl` に追記し、反応のやり方ごとの結果を `LEARN_DAYS`（既定30日）分集計して `stats` に入れる。10分ごとにログへ集計を出す。
- 30分ごとに `NEWS_FEEDS` の Yahoo!ニュース・トピックスの見出しを取り、`NEWS_BLOCK` の言葉を含む見出しを除いて `news` に入れる。

### 4.3 ritsu_base（コンテナ ritsu-base）

**制御ループ（1秒に20回）**

上から順に見て、最初に当てはまった動きを使う。

| 順 | 条件 | 動き |
|---|---|---|
| 1 | 十字ボタンの `/cmd_vel` が0.5秒以内に来ている | その速さ（向く・少し動く・おさんぽ・フォローはやめる） |
| 2 | 少し動く途中 | 決めた距離・角度まで（エンコーダーで測る。測れなければ時間で） |
| 3 | フォロー中 | `follow_cmd()`（下の表） |
| 4 | 人の方を向く途中 | 顔のずれ × 1.2 の速さで回る（0.2〜0.4rad/s）。5度以内で止まる |
| 5 | おさんぽ中 | `walk_cmd()`（行き先は LLM、使えなければ `walk_decide()`） |
| 6 | どれでもない | 止まる |
| 最後 | 安全装置 | 正面の障害物が0.4mより近ければ前進（vx > 0）だけ 0 にする。頼まれた前進なら `blocked` を知らせる |

その後、メカナムの式で4輪の速さにし、`MAX_LINEAR` 0.3m/s・`MAX_ANGULAR` 1.2rad/s で制限して `base_set` を送る。

**メカナムの式**（L = `WHEEL_LX` ＋ `WHEEL_LY`）

| 車輪 | 速さ |
|---|---|
| 左前 | vx − vy − L・wz |
| 右前 | vx ＋ vy ＋ L・wz |
| 左後 | vx ＋ vy − L・wz |
| 右後 | vx − vy ＋ L・wz |

`WHEEL_INVERT` で向きが逆の車輪を反転する。エンコーダーの値から逆の式で `/odom` を求める。

**follow_cmd()**

| 状態 | 動き | `/remote` に出る状態 |
|---|---|---|
| 人がまだ決まらない | 待つ。5秒で `nobody` としてやめる | find |
| 見失った | 待つ。4秒で `lost` としてやめる | lost |
| ずれが40度以上 | 進まずに向く | turn |
| 人まで0.8mより近い | 止まって待つ（ずれ20度以内なら回らない） | near |
| それ以外 | `follow_decide()` | forward / left / right / wait |

- 向く速さ: ずれ × ゲイン（最大0.45rad/s）。ずれ12度以内なら回らない。
- 進む速さ: (人までの距離 − 0.7m) × 0.5、最大0.15m/s。ずれが大きいほど遅くする。

**follow_decide()（Jev と同じ形）**

| 条件（人を除いた障害物） | 答え | 動き |
|---|---|---|
| 正面の物が0.6mより遠い | FORWARD | 人へ進む |
| 左だけ空いている（0.5m より遠い） | LEFT | 向きを変えずに左へ 0.08m/s |
| 右だけ空いている | RIGHT | 向きを変えずに右へ |
| 両方空いている | 人のいる側 | 同上 |
| 両方ふさがっている | WAIT | 待つ。`blocked`（by follow）を知らせる |

**walk_cmd()（行き先は LLM に選ばせる）**

| 場面 | LLM に出す選択肢 | 答えを待つ間 | 答えの動き |
|---|---|---|---|
| 正面の物が0.7mより近い | LEFT / RIGHT のうち空いている側（0.8mより遠い）。両方ふさがっていれば両方 | 止まる（`walk: "think"`） | その場で 0.5rad/s で回り、正面が空いたら進む。200度回っても空かなければやめる |
| 広い所（8秒ごと、始めて2秒で最初） | FORWARD ＋ 空いている側 ＋ PERSON（人が10度以上横・1.0mより遠くに見えている） | 0.08m/s で進む | LEFT / RIGHT は40度回ってまた進む。PERSON は人の方へ回ってまた進む（`walk: "person"`） |

- 選択肢が1つしか無いときは聞かない。
- 問い合わせは別のスレッドで、`http://127.0.0.1:8080/llm/v1/chat/completions`（nginx が API キーを付ける）へ。model `chat`、temperature 0.7、max_tokens 12、`response_format` の JSON Schema で `action` を選択肢の enum に縛る。答えの中から選択肢の語を拾う。
- LLM に渡す文: 前・左・右の空き（「1.2m 先に物がある」「物は見えない」）、人（「右に30度、1.5m 先」）、スタートから見た今の向き、始めてからの秒数、最近選んだ動き（4つまで）、選択肢。
- 2秒（`WALK_LLM_TIMEOUT`）で答えが無ければ `walk_decide()`（下）。つながらなければ60秒は聞かない。

**walk_decide()（決まりごと。Jev と同じ形）**

| 条件 | 答え |
|---|---|
| 正面の物が0.7mより遠い | FORWARD |
| 正面がふさがっている | LEFT / RIGHT（空いている方・両方なら広い方） |

**カメラの知らせが途切れたとき**: 障害物の知らせが1秒より古いと、おさんぽ・フォローはその場で止まって待つ。5秒続いたらやめる（`why: "camera"`）。

## 5. マイコン（sketch.ino）

- 4輪の速さを PI 制御で50回/秒合わせる。PWM は220まで。
- エンコーダーの A 相を割り込みで数え、B 相で回った向きを読む（B 相の極性は最初に少し回したときに自動で合わせる。読めない車輪は指令の向きとみなす）。
- 強く回しているのに1秒回らない車輪は止める（ロック検出）。
- `base_set` が0.5秒来なければ全輪を止める。
- EN のピンには `pinMode()` をしない（UNO Q では `analogWrite` の PWM が出なくなる）。

## 8. エラー処理

| 起きること | 処理 |
|---|---|
| LLM が答えない・遅い | 反応は4秒、動く頼みの聞き分けは2.5秒で打ち切り、用意したセリフか普通の会話にする。LLM ランプを黄（遅い）か灰（失敗）にする |
| rosbridge が切れた | ros.js が自動で再接続し、購読をやり直す。ROS ランプを灰にする |
| カメラの映像が来ない | 10秒で開き直す。30秒処理が進まなければプロセスを終了（Docker が起動し直す） |
| カメラの知らせが台車に来ない | おさんぽ・フォローは止まって待ち、5秒でやめて律が知らせる |
| STM32 とつながらない | ritsu-base がログに出し、つながるまで送り直す |
| memory.json が壊れた | 起動時に一番新しい控えから戻す |
| 指令が途切れた | 台車のノードは0.5秒、マイコンも0.5秒で止める |
